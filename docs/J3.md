# J3, sécuriser et fiabiliser le système IoT

Protocole suivi pour chaque scénario : hypothèse commitée avant le test, injection, observation,
explication, décision, rejeu après correction.

## Comment distinguer sans ambiguïté plusieurs capteurs qui publient en parallèle ?

Par le `device_id`, dans le topic et dans le message, et le backend exige qu'ils soient égaux.
`room_id` ne suffit pas car notre registre peut le changer. Le `device_id` est aussi dans la clé
d'unicité `(device_id, message_id, recorded_at)` et dans chaque trace. Ça empêche une
incohérence, pas une usurpation : le kit n'a qu'un compte MQTT. Scénario 2.

## Quelles données entrantes doivent être refusées avant d'atteindre le cœur du système ?

Cinq cas, refusés par le job de consolidation et pas par le consommateur MQTT :

- JSON illisible : rien à valider.
- Champ obligatoire absent ou mal typé : le schéma Zod est le contrat.
- Valeur hors des bornes du capteur : l'objet est en panne.
- Date d'observation dans l'avenir : elle bloquerait l'état courant.
- `device_id` différent entre topic et message : incohérence d'identité.

Le message est d'abord écrit dans la zone brute, donc un refus garde son contenu et son motif.
On borne sur le capteur et pas sur le kit (420 à 2500 ppm), pour garder les valeurs anormales
mais vraies.

## Comment détecter qu'un capteur ne fournit plus une information suffisamment fraîche ?

Le backend compare l'heure d'observation de la dernière mesure à la sienne, seuil 30 secondes,
et l'expose dans `is_stale`. Pas sur le téléphone, car son horloge peut différer. Depuis J3, le
job écrit une ligne à chaque bascule. Un capteur en pause garde `availability` à `online`. Scénario 6.

## Comment le système se comporte-t-il face à un message dupliqué, retardé ou invalide ?

- Doublon : écarté par `ON CONFLICT DO NOTHING`, car un test applicatif raterait deux
  traitements simultanés. Il est tracé.
- Retard : entre dans l'historique, mais ne remplace l'état courant que s'il est plus récent.
  `retardMs` le signale.
- Invalide : jamais une mesure, et le service continue.

## Que se passe-t-il si le broker MQTT devient indisponible puis revient ?

Le backend le trace et se reconnecte toutes les 2 secondes. L'API répond toujours. Rien n'est
perdu, mais seulement parce que le simulateur suspend ses mesures. D'où le scénario 8, qui coupe
le backend.

## Quels secrets ne doivent jamais être versionnés ?

Le mot de passe de la base, la clé de signature des jetons, celui de l'interface de logs, et tout
identifiant qui ouvre autre chose que cette machine. Ils sont dans `.env`, ignoré par Git, et
listés sans valeur dans `.env.example`.

Le dépôt est public, donc on a vérifié tout l'historique : aucun `.env`, aucune clé ni
certificat. Seuls traînent les identifiants de démonstration de l'école et celui d'un conteneur
jetable de J2.

```sh
git log --all --pretty=format: --name-only --diff-filter=A | sort -u | grep -E "^\.env$"
git ls-files | grep -iE "\.(pem|key|p12|pfx)$|id_rsa"
```

`API_PORT`, `COMPOSE_PROJECT_NAME` et `LOG_LEVEL` manquaient dans `.env.example`. Ajoutés.

## Journalisation et recherche

Stack Alloy, Loki, Grafana : voir `docs/observabilite.md`. Le backend émet maintenant les champs
imposés, avec un `eventId` créé à la réception et repris par le job, ce qui relie réception et
traitement.

| Recherche demandée | Requête LogQL |
|---|---|
| Tous les événements d'un objet | `{service_name="backend"} \| json \| deviceId="sensor-001"` |
| Messages rejetés et leur motif | `{service_name="backend"} \| json \| eventType="mesure_rejetee"` |
| Doublons détectés | `{service_name="backend"} \| json \| eventType="doublon_ecarte"` |
| Données devenues anciennes | `{service_name="backend"} \| json \| eventType="mesure_ancienne"` |
| Erreurs de connexion au broker | `{service_name="backend"} \| json \| eventType=~"broker_.*"` |
| Parcours complet d'une mesure | `{service_name="backend"} \| json \| eventId="<identifiant>"` |

`reason` est un code fixe, donc `sum by (reason) (...)` compte les refus par motif. Tableau de
bord en lecture seule sur <http://localhost:3001> : `docs/preuves/J3-tableau-de-bord.png`.

## Risques identifiés et stratégie

Six risques retenus avant les tests, d'après le contrat du kit et les manques de J2 :

- Mesure attribuée au mauvais objet : `device_id` comparé entre topic et message, présent dans
  toutes les clés.
- Objet imité : détection par la session annoncée, car le kit n'authentifie pas les objets.
- Donnée fausse affichée ou qui gèle l'état courant : refus hors bornes et des dates futures,
  avant écriture.
- Valeur périmée vue comme fraîche : fraîcheur calculée par le backend, bascule journalisée.
- Perte d'un composant : session MQTT persistante, perte résiduelle mesurée.
- Secret publié sur le dépôt public : variables d'environnement, historique Git vérifié.

## Synthèse par incident

Détectés, sans perte ni action, avec reprise automatique : payload invalide (motif et message
brut gardés), doublon, mesure retardée, mesure datée de l'avenir, message retained ancien,
broker indisponible (le simulateur suspend ses mesures). Les autres :

- Capteur silencieux : détecté à la bascule, bascule inverse au retour.
- Usurpation : détectée mais pas empêchée, historique pollué. Action : un compte MQTT par objet,
  hors du kit.
- Backend indisponible : perte et reprise partielles, mesurées. Action : accepter la perte ou
  publier en QoS 2.
- Montée en charge : retard croissant, pas de perte jusqu'à 101 msg/s, la file se résorbe.
  Action : surveiller le retard de consolidation.

## Fonctionne

- Les trois capteurs sont distingués partout.
- Les cinq cas d'entrée fautive sont refusés avec un motif, sans arrêt du service.
- La bascule en donnée ancienne est tracée une fois, dans les deux sens.
- Une mesure se suit par son `eventId`, de la réception MQTT à l'écriture.
- Les onze scénarios obligatoires ont suivi le protocole en six temps.
- Aucun secret réel dans l'historique Git.
- 42 tests automatisés sur le backend, contre 27 à la fin de J2.

## Incomplet ou en échec

- Usurpation détectée mais pas empêchée, faute d'un compte MQTT par objet.
- Coupure du backend de 30 secondes : 12 messages sur 45 rejoués, 36 perdus. La part rejouée
  varie entre 0 et 12, seul l'écart entre QoS 0 et QoS 1 est reproductible.

## Limites ou dette connue

- Le `boot_id` de détection de session est en retained, donc copiable par qui lit le topic
  `state`.
- Une date future est tolérée 10 secondes, le temps pour une fausse mesure de prendre l'état
  courant.
- À 101 messages par seconde, le job passe de 5 à 15 secondes. Le seuil de fraîcheur tient, avec
  moins de marge.
- La surveillance de fraîcheur est en mémoire : une bascule pendant un redémarrage du backend
  n'est pas tracée.
- Rien n'est chiffré. Voir `docs/securite.md`.
